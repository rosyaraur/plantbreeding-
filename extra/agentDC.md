Building an intelligent data engine on top of a robust statistical foundation is a fantastic project. Looking at your current setup, you already have a strong foundation with your domain logic cleanly separated into `python_package` and `r_package`.

To turn this repository of scripts into an autonomous or semi-autonomous "agent" (like a Data Intelligence Engine), you need to introduce an orchestration layer. Modern AI agents (built with frameworks like LangChain, LlamaIndex, or AutoGen) primarily run in Python. Therefore, your Python environment will serve as the "brain," acting as a bridge to both your native Python functions and your R scripts.

Here is how you can restructure your project to make it "agent-ready."

### Proposed "Agent-Ready" Architecture

I recommend wrapping your existing packages inside a larger application structure. You don't need to rewrite your statistical code, but you do need to create "tool wrappers" that teach the LLM how to use them.

```text
plantbreeding_engine/
│
├── agent_core/              # NEW: The "Brain" of your engine
│   ├── __init__.py
│   ├── orchestrator.py      # Main agent logic (e.g., Langchain ReAct agent)
│   ├── prompts.py           # System instructions telling the agent what it is
│   └── state.py             # Memory and conversation history management
│
├── tools/                   # NEW: The "Hands" of your engine
│   ├── __init__.py
│   ├── tool_registry.py     # Maps natural language requests to specific tools
│   ├── python_wrappers.py   # Pydantic/JSON wrappers for `python_package`
│   └── r_wrappers.py        # Wrappers for `r_package` (via rpy2 or subprocess)
│
├── core_logic/              # EXISTING: Your current analytical code
│   ├── python_package/      # (Move your python_package here)
│   └── r_package/           # (Move your r_package here)
│
├── api/                     # NEW: How users/frontends talk to the agent
│   ├── server.py            # FastAPI or Flask app
│   └── routes.py            # Endpoints (e.g., /chat, /analyze)
│
├── workspace/               # EXISTING: Agent scratchpad
│   ├── inputs/              # Datasets uploaded by the user
│   └── outputs/             # Plots (like GGE biplots), CSVs, and logs generated by the agent
│
├── documentation/           # EXISTING: Your docs
│└── requirements.txt        # Python dependencies (Langchain, FastAPI, rpy2, etc.)

```

### Key Components Explained

**1. The `tools/` Directory (Crucial Step)**
LLMs cannot run code directly; they can only output text (like JSON). You must create a translation layer. For every script (e.g., `calculate_audpc.py` or `ammi.full.r`), you need a wrapper function that tells the LLM:

* **Name:** `calculate_audpc`
* **Description:** "Calculates the Area Under the Disease Progress Curve. Use this when the user asks about disease progression over time."
* **Arguments:** `time_points` (List of integers), `disease_severity` (List of floats).

**2. Handling the R Package (`r_wrappers.py`)**
Since your Python package is a subset of your R package, the agent will need to call R when a specific Python equivalent doesn't exist. You have two main ways to handle this in your wrappers:

* **`rpy2`:** A Python library that allows you to run R code seamlessly within Python. This is elegant but can sometimes be tricky to set up across different operating systems.
* **Subprocess CLI:** Have your wrapper save the agent's parameters to a temporary JSON file, run a command line call (e.g., `Rscript my_r_script.R --args input.json`), and then read the output file.

**3. The Orchestrator (`agent_core/orchestrator.py`)**
This is where the magic happens. You will initialize an LLM and give it access to your `tools/` registry. When a user says, *"Can you run an AMMI analysis on this yield data?"*, the orchestrator will:

1. Parse the user intent.
2. Search the tool registry for "AMMI analysis".
3. Notice `ammi_full` requires a dataset.
4. Extract the dataset from the `workspace/` and format the arguments.
5. Execute the Python or R function.
6. Read the statistical output and summarize the findings back to the user in natural language.

Let's build the "Brain" of your engine. The `agent_core` directory is responsible for managing the AI's persona, its memory, and how it routes user requests to your statistical tools.

Since you need a framework that heavily relies on tool-calling (routing between Python and R scripts), we'll look at this through the lens of a standard **LangChain** or **LlamaIndex** setup, which are the industry standards for this kind of architecture.

Here is a detailed breakdown of what goes inside each file in `agent_core/`.

### 1. `prompts.py` (The Persona and Rules)

This file holds the system instructions. It defines *who* the agent is, *how* it should behave, and *what* rules it must follow when using your statistical tools.

```python
# agent_core/prompts.py

SYSTEM_PROMPT = """
You are the Plant Breeding Data Intelligence Engine, an expert agronomic and statistical AI. 
Your goal is to assist plant breeders and geneticists in analyzing their field trial data.

You have access to a suite of specialized tools for both R and Python. 
When a user asks you to perform an analysis (e.g., AMMI, AUDPC, GGE Biplots):
1. Identify the correct tool for the job.
2. Check if you have the required dataset in the workspace. If not, ask the user for it.
3. Execute the tool.
4. Interpret the statistical output (like p-values, variance, or disease severity) and explain it to the user in clear, scientifically accurate language.

Constraints:
- Never make up statistical results. Only report what the tools output.
- If a tool fails, explain the error to the user and suggest how to fix the input data.
- Always be precise about whether you are reporting genotypic or phenotypic variances.
"""

```

### 2. `state.py` (Memory and Context)

Agents need to remember what happened earlier in the conversation and what files they are currently working on. This file defines the data structures for that memory.

```python
# agent_core/state.py
from typing import List, Optional
from pydantic import BaseModel

class AgentState(BaseModel):
    """Tracks the current context of the conversation."""
    session_id: str
    chat_history: List[dict] = []
    current_active_dataset: Optional[str] = None  # e.g., "workspace/inputs/yield_trial_2026.csv"
    last_generated_plot: Optional[str] = None     # e.g., "workspace/outputs/gge_biplot.png"

    def update_dataset(self, filepath: str):
        self.current_active_dataset = filepath
        
    def add_message(self, role: str, content: str):
        self.chat_history.append({"role": role, "content": content})

```

### 3. `orchestrator.py` (The Main Engine Loop)

This is the core execution file. It initializes the LLM, binds your tools (from the `tools/` folder we discussed earlier), and runs the reasoning loop (often called a ReAct loop: Reason, Act, Observe).

```python
# agent_core/orchestrator.py
from langchain.chat_models import init_chat_model
from langchain.agents import AgentExecutor, create_tool_calling_agent
from langchain_core.prompts import ChatPromptTemplate
from agent_core.prompts import SYSTEM_PROMPT
from tools.tool_registry import get_all_tools # This imports your R/Python wrappers

class PlantBreedingAgent:
    def __init__(self, model_provider="google", model_name="gemini-2.5-pro"):
        # 1. Initialize the LLM
        self.llm = init_chat_model(model_name, model_provider=model_provider)
        
        # 2. Load the tools (your R and Python wrappers)
        self.tools = get_all_tools()
        
        # 3. Set up the prompt template
        self.prompt = ChatPromptTemplate.from_messages([
            ("system", SYSTEM_PROMPT),
            ("placeholder", "{chat_history}"),
            ("human", "{input}"),
            ("placeholder", "{agent_scratchpad}"),
        ])
        
        # 4. Create the Agent
        agent = create_tool_calling_agent(self.llm, self.tools, self.prompt)
        self.agent_executor = AgentExecutor(agent=agent, tools=self.tools, verbose=True)

    def run(self, user_input: str, chat_history: list = None):
        """Entry point for the API or UI to talk to the agent."""
        if chat_history is None:
            chat_history = []
            
        response = self.agent_executor.invoke({
            "input": user_input,
            "chat_history": chat_history
        })
        
        return response["output"]

```

### 4. `__init__.py` (The Exporter)

This keeps your imports clean so your API server can easily grab what it needs.

```python
# agent_core/__init__.py
from .orchestrator import PlantBreedingAgent
from .state import AgentState

__all__ = ["PlantBreedingAgent", "AgentState"]

```

### How they work together

When a user interacts with your system:

1. The user's message goes to `orchestrator.py`.
2. `orchestrator.py` injects the `SYSTEM_PROMPT` and the user's message into the LLM.
3. The LLM decides it needs to calculate disease progression. It tells `orchestrator.py` to use the `calculate_audpc` tool.
4. `orchestrator.py` calls the wrapper in your `tools/` directory, which in turn runs your actual math logic.
5. The result comes back to the LLM, which formats it into a nice response for the user.

To bring this architecture to life, especially when running local LLMs via Ollama, the next crucial step is building out the `tools` directory. This is where you create the "bridge" that allows the LLM to understand and execute the scripts living inside your `core_logic` folder.

Here is how you can structure the contents of the `tools` directory.

### 1. `python_wrappers.py` (The Translation Layer)

Local models need very clear descriptions of what a function does and exactly what inputs it requires. Using LangChain's `@tool` decorator is an excellent way to expose your `python_package` functions to the local LLM.

Let's create a wrapper for your `calculate_audpc.py` script as an example:

```python
# tools/python_wrappers.py
from langchain_core.tools import tool
from typing import List

# Import the actual analytical logic from your existing package
from core_logic.python_package.calculate_audpc import calculate_audpc as native_audpc
# from core_logic.python_package.gge_biplot_analysis import run_gge ... etc.

@tool
def calculate_audpc_tool(time_points: List[int], severity: List[float]) -> float:
    """
    Calculates the Area Under the Disease Progress Curve (AUDPC).
    Use this tool to evaluate disease resistance in plant varieties over time.
    
    Args:
        time_points: A list of integers representing the days measurements were taken.
        severity: A list of floats representing disease severity percentages.
    """
    try:
        # Here we pass the LLM's parsed arguments into your raw statistical function
        result = native_audpc(time_points, severity)
        return f"The calculated AUDPC value is: {result}"
    except Exception as e:
        return f"Error calculating AUDPC: {str(e)}. Please check your input arrays."

# You would continue wrapping other functions here...

```

### 2. `tool_registry.py` (The Tool Manager)

As you wrap more of your Python and R scripts, you'll want a centralized place to gather them up so your orchestrator can easily load them.

```python
# tools/tool_registry.py
from .python_wrappers import calculate_audpc_tool
# from .r_wrappers import ammi_analysis_tool

def get_all_tools():
    """
    Returns the complete list of tools available to the Data Intelligence Engine.
    The orchestrator uses this list to bind tools to the LLM.
    """
    return [
        calculate_audpc_tool,
        # ammi_analysis_tool,
        # add your other tools here as you build them
    ]

```

### 3. Updating the Orchestrator for Local Execution

With your tools defined, your orchestrator inside `agent_core/orchestrator.py` can now pull in a local Ollama model and bind these specific tools to it.

```python
# snippet for agent_core/orchestrator.py
from langchain_ollama import ChatOllama
from tools.tool_registry import get_all_tools

# Initialize your local model (e.g., Llama 3 or Mistral running via Ollama)
llm = ChatOllama(model="llama3")

# Fetch your wrapped Python/R functions
tools = get_all_tools()

# Bind the tools to the LLM so it knows they exist
llm_with_tools = llm.bind_tools(tools)

```
